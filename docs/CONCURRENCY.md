# 多用户并发访问检查说明

本文档记录对「错题本」项目在多用户并发场景下的检查结果与已做加固。

## 1. 已确认无问题的部分

### 1.1 请求隔离
- **DB 会话**：每个请求通过 `get_db()` 获得独立的 `AsyncSession`，请求结束时 commit/rollback 并 close，无跨请求共享会话。
- **当前用户**：`get_current_user_id` 从请求头 JWT 解析，无服务端共享状态，多用户请求互不干扰。

### 1.2 数据隔离
- 所有列表/详情接口均按 `user_id` 或 `require_subject_owner` 过滤，用户只能访问自己的科目/章节/题目/复习数据。

### 1.3 文件存储
- 头像、题目图、导出 PDF 均使用 `uuid.uuid4().hex` 生成文件名，并发上传不会互相覆盖。
- 文件按类型分目录（avatars/questions/pdfs），访问路径带 UUID，无越权读写的路径风险。

### 1.4 全局单例
- **OpenAI 客户端**（`llm._openai_client`）：懒加载单例，`AsyncOpenAI` 为无状态、可并发调用，多请求共用同一 client 无问题。
- **Coze 调用**：每次请求新建 `httpx.AsyncClient()`，无共享状态。

---

## 2. 已修复的并发问题

### 2.1 微信登录：同一 openid 并发创建用户
- **问题**：两个请求同时用同一 openid 登录时，都可能通过「查无用户 → 创建用户」，导致第二次 `db.flush()` 触发 `IntegrityError`（openid 唯一约束），请求 500。
- **修复**：在 `auth.wechat_login` 中捕获 `IntegrityError`，执行 `rollback` 后重新查询该 openid 对应用户，再继续更新昵称/头像并返回 token；若仍查不到则返回 500「登录冲突，请重试」。

### 2.2 删除科目与添加题目的竞态
- **问题**：删除科目时先 `count(Question)` 再 `delete(Subject)`。若在两者之间另一请求向该科目添加了题目，可能删掉本应受「有错题则不可删除」保护的科目，或导致刚添加的题目被 CASCADE 删掉。
- **修复**：
  - 删除科目时对 `Subject` 使用 `select(...).with_for_update()`，在事务内加行锁后再 count 再删除。
  - 创建题目时使用 `require_subject_owner_for_update`（内部对 Subject 使用 `with_for_update()`），与删除科目互斥。这样「删科目」与「在该科目下加题」会串行化，避免上述竞态。

---

## 3. 可接受的竞态（未改）

### 3.1 复习提交结果
- **行为**：`POST /reviews/{question_id}/result` 读题目当前 `interval_days`/`review_stage`，计算下次复习日并写回。
- **竞态**：同一题目被两个请求几乎同时提交结果时，后写覆盖前写，复习计划以最后一次提交为准。
- **结论**：业务上同一用户对同一题一般不会并发提交两次，即便发生也是「最后一次生效」，可接受，未加锁。

---

## 4. 小结

- 多用户并发下：**请求隔离、数据按用户隔离、文件命名唯一** 均无问题。
- **登录重复创建用户**、**删科目与加题** 两处已做并发加固（IntegrityError 处理 + FOR UPDATE 互斥）。
- 其余写操作为「按资源归属校验后单次更新」，无读-改-写长事务竞态要求，当前实现可满足多用户并发使用。
